# Scanner inventory: products, services and checks

Derived from the code on 2026-10-21 (not from marketing copy). **This is the single source of truth for per-check detail.** The module-level prose that used to duplicate it in `CLAUDE.md`'s, and later `docs/ARCHITECTURE-NOTES.md`'s, "Scanner pipeline" section was merged into this file on 2026-10-21, claim by claim against the code; that section is now a pointer here and keeps only the two-tier wiring and the order of the final passes. For how a check is plan-gated or tested, see `docs/FUNCTIONALITY-MATRIX.md`; for the rules a new check must follow, `docs/SCANNER-CONVENTIONS.md`.

Where `docs/FUNCTIONALITY-MATRIX.md` or `src/app/what-we-check/page.tsx` disagree with the code, the code wins; see "Discrepancies noticed" at the end, which also records every disagreement the merge turned up and which document had been right. Paths are relative to `hebridescyber-app/` unless prefixed `../`.

## 0. How a scan is structured

| Tier | Entry point | Runs when |
|---|---|---|
| Base passive suite | `runAllChecks()` + `summariseResults()` in `src/lib/scanners/index.ts` | Every scan: on-demand, API, scheduled. Needs no binaries except Chromium (Playwright). |
| Extended active-tool suite | `runExtendedTools()` in `src/lib/scanExecution.ts` (plus `runCloudPostureChecks()`), gated per tool by `resolveToolConfig()` in `src/lib/scanProfiles.ts` | Only when the resolved scan profile is not `safe`. On-demand jobs (job has `scan_id`) are always `safe`; scheduled jobs use the target's `scan_profile` (column default `full`) or its `scan_bundle_id`. Binaries are installed only in `../.github/workflows/scheduled-scans.yml`. |

Final passes (all in `executeScan()` / `summariseResults()`), in order:

1. `meta.no-issues` info finding if nothing else was found.
2. Compliance mapping (`compliance.ts`: Cyber Essentials, OWASP Top 10, CIS Controls v8, ISO 27001, PCI DSS, NIS2, DORA, SOC 2, HIPAA; the last two *derived* from those rows by the small `CROSSWALK` table, so there is one line to dispute per objective rather than 150 rows — an automated indicator, never an attestation) and fix difficulty / minutes estimate (`fixDifficulty.ts`: trivial/easy/moderate/hard), both keyed on the `checkId`'s base (the part before its first `:`). Applied to base findings in `summariseResults()` and again to extended and cloud-posture findings in `executeScan()`. A checkId with no entry gets no refs — meaning "not yet categorised" or "genuinely doesn't fit", never a forced mapping. Neither is ever set at an individual push site. The same passes add `attackRefs` and `cwe` (`attackMap.ts`): the MITRE ATT&CK technique an adversary could use against the exposure, and the CWE weakness id, curated per finding *type* (IDs, names and links only, never attack detail). The executive report prints them, with MITRE's attribution, and maps older scans from their checkId at render time.
3. Drop `recon.subdomains-found` if Subfinder returned results.
4. Cross-tool consolidation (`findingConsolidation.ts`): extended-tool duplicates are folded into one canonical finding with `corroboratedBy`. Own base checks always win; only extended-tool findings are dropped.
5. CVSS v3.1 enrichment from NVD (`cvssEnrich.ts`), best-effort.
6. Threat intel (`threatIntel.ts`), run right after CVSS enrichment: every CVE-backed finding gets CISA KEV membership (and ransomware use) plus the highest FIRST EPSS score across its CVEs. Both feeds are free and keyless; KEV is cached per worker process. It never changes `severity` — that is the finding's own evidence — but the report sorts known-exploited and higher-EPSS findings first *within* a severity and shows badges. Absent `threatIntel` means unknown, never "not exploited": `knownExploited: false` is only written when the feed was actually read.
7. False-positive triage exclusion, then AI summary (Azure OpenAI if configured, else templated), then `scoreFromFindings()`: 100 minus each finding's penalty (`scanners/riskScore.ts`) — flat severity penalties of critical 30 / high 15 / medium 7 / low 2 / info 0, each raised to at least the CVSS band's penalty, multiplied for CISA KEV (1.5x, 2x if ransomware) and high EPSS, and lowered (0.75x) only for a *measured* EPSS below 0.01 on a non-KEV finding. Capped at 45 per finding, floored at 0. A finding with no CVSS or intel costs exactly its flat penalty, so most scores are unchanged, and stored scores are never rewritten.
8. After completion: finding lifecycle, asset inventory sync, alerts and webhooks (not scanner checks).

## Part A: Products and services used

### A(a) Open-source binaries and daemons run by the scanner

All are invoked as separate processes or over HTTP (ZAP). Every wrapper returns `not_configured` (or `not_applicable`) rather than failing the scan when the binary is missing. All installs are in `../.github/workflows/scheduled-scans.yml` (job `work`) unless stated. `on-demand-scan.yml` installs none of them (only Playwright Chromium).

Every wrapper shells out through `src/lib/execTool.ts`'s `execTool`, never bare `execFile`/`promisify(execFile)`: `execTool` closes the child's stdin, without which tools that read targets from stdin (nuclei, gospider) hang until their timeout — which is why every scheduled scan's nuclei step produced nothing until it was found.

**Retired:** xsser was removed in E-72b. It is not installable on the runner image (no apt package on Ubuntu 24.04, and the pip build crashes at import because it only runs from inside its own source checkout), so it had only ever returned `not_configured`. ZAP covers XSS, and reflected-XSS confirmation lives in `proofOfExploit.ts`.

## Part B: Checks performed against a target

Severity shown is what the code assigns (or the range). "Needs" lists non-default prerequisites.

### B1. Base passive suite (every scan)

Wired in `runAllChecks()`; findings derived in `summariseResults()` unless noted. Always runs, on every scan, regardless of plan or repo connection.

`runAllChecks()` runs most of these in two `Promise.allSettled` batches — 17 independent read-only probes first, then Playwright, `webapp`, the ZAP spider start and the passive API-spec check — and resolves the rest in dependency order, because each needs an earlier result as input: `crawler.ts` (seeded by `waybackDiscovery`'s live paths), then `scriptInventory.ts` and `cookieConsent.ts` (both need Playwright's runtime capture), `wpvdb.ts` (needs `webapp`'s WordPress plugins/themes), `softwareCveDb.ts` (needs `fingerprint`'s `riskySoftware`), `takeover.ts` + `subdomainCerts.ts` (both need `recon`'s CT subdomains) and `endOfLife.ts` (needs `fingerprint` + `webapp` versions). A crashed check is unwrapped to its own `status: "error"` shape, never allowed to fail the scan.

If the CT lookup failed (`recon.ctLookupFailed`), `takeover.ts` and `subdomainCerts.ts` report `error`, never an empty "checked" — crt.sh is often down, and an empty list would mark every open subdomain finding fixed and close its tickets.

### B2. Extended active-tool suite

Opt-in only, gated per tool by the scan's resolved profile — in practice scheduled jobs only. Real binaries and daemons that exist only in that GitHub Actions job.

Findings are built in `runExtendedTools()` (`src/lib/scanExecution.ts`) unless the module builds `Finding[]` itself. Profiles: **F**=full, **A**=api, **C**=cms, **O**=osint; `offensive` and `ai-pentest` enable every tool key, so they are not repeated per row. Retest of any of these on an on-demand scan is blocked by `src/lib/extendedToolCheckIds.ts`.

A tool its profile disables resolves to exactly the same `not_configured`/`not_applicable` shape its own module returns when its binary, repo or credential is missing. That is deliberate: the findings-derivation block after the batch needs no profile awareness, because a profile-disabled tool is indistinguishable from "not available in this environment", which it already handles by pushing nothing.

Three tools run outside the main `Promise.allSettled` batch, all inside `runExtendedTools()`: `httpx` (needs `subdomains`' discovered hostnames), `contentDiscovery` and `credentialSpray` (offensive-only, probe the target directly). `metadataLeak` runs after the batch too, since it consumes the URLs Photon and Gospider found. `cloudPosture` runs in `executeScan()`, outside `runExtendedTools()` entirely.

### B4. Cross-cutting mechanics every check shares

The normative rules live in `docs/SCANNER-CONVENTIONS.md`; this is what they look like in practice.

**Remediation text** lives in `src/lib/scanners/remediationText.ts` and is attached as `Finding.remediation` **at the point the finding is created**, where the check result is still in scope. The field is optional because scans stored before it existed deserialise without it, so every consumer must guard. Never re-derive which fix applies by string-matching a finding's title.

**False-positive baselining.** `exposure.ts` fetches a random-slug URL alongside the site root to learn what a "not found" response looks like, masks the probed path out of both bodies, and discards any probe whose body matches that baseline. Without this, every SPA that returns its shell for unknown paths reports an exposed `.env`. Any new check that probes for a file must reuse `fetchBaseline`/`normaliseBody` (`httpProbe.ts`) rather than trusting a 200 status. `directoryListing.ts` reuses the same baseline/masking.

**Evidence states and what they mean to the lifecycle.** `checked` is a real verdict; `error` is "the lookup failed"; `partial` is "ran, but didn't see everything" (a page cap, time budget, 429/503, or a headless browser that didn't start); `not_applicable` is "there was nothing here to check". `findingLifecycle.ts` treats `error` and `partial` as **not run**, so neither resolves last scan's findings as fixed or closes their tickets. This is why a failed lookup is never an empty `checked`.

**Which domain a hostname belongs to** is always `registrableDomain.ts`, never hand-rolled suffix logic: `registrableDomain` (ICANN suffixes — the domain registered at a registry, used for RDAP, `dns.ts`'s email authentication and HIBP) and `ownerDomain` (private suffixes too — the narrowest domain one customer controls, used to scope hostnames in `recon.ts`, `takeover.ts`, `subdomainCerts.ts`, `scriptInventory.ts`, `cookieConsent.ts` and the attack-surface alerts, so `mysite.github.io` never takes in other github.io sites). Both come from the full Public Suffix List via `tldts`. A hand-picked list once mapped `www.school.herts.sch.uk` to the whole county's zone.

**Login recording** (`src/lib/scanners/loginRecorder.ts`, `POST /api/account/record-login`) drives a real headless browser through the target's own login form — fill username + password, press Enter so the page's own CSRF token travels with the submit — and saves the resulting cookies as a normal `target_auth_credentials` row. It is the alternative to pasting a session cookie by hand, for a plain form with no MFA step. Same Agency gate and ownership check as `target-auth.ts`, plus: session auth only, rate-limited, `loginUrl` must be on the target's own host and `https://`, and the caller must send `acknowledged: true`. The password is used once and never logged, stored or returned. UI: `MonitoredTargets.tsx`'s `AuthenticatedScanConfig` has a third "Recorded login" tab alongside "Session cookie" and "Basic Auth". A public-facing consent-wording review is still owed — see `docs/AUTHENTICATED-CRAWL.md`.

## Part C: What is deliberately not done

From `docs/USER-GUIDE.md` section 6 and `docs/COMPETITIVE-ANALYSIS.md` section 9, as stated policy:

- No brute-forcing and no destructive payloads on any plan below Tier A; active tools run only
  against ownership-verified domains. **Tier A** is an explicit, per-target opt-in exception: once
  authorized, it sends real attack traffic — bounded content/path discovery (a brute-force of a
  curated path list), credential-defence testing, and, where separately enabled, real credential
  spraying against a designated test account and real exploitation. See
  `docs/USER-GUIDE.md` §6 and `FUNCTIONALITY-MATRIX.md`'s Tier A rows for the gating detail.
- No fabricated findings: a check that cannot evidence something reports nothing (hence `error` / `partial` / `not_applicable` states that never resolve findings as fixed).
- No deep IDOR testing, no multi-step auth (OAuth/MFA) handling. Authenticated scanning (a saved
  session cookie or Basic Auth credential) does run a real signed-in crawl across every page it can
  reach while logged in (`authenticatedCrawl.ts`), plus a narrow check for a handful of common API
  paths that answer without authorisation — it does not test whether one logged-in user can reach
  another user's specific data, and it never attempts an OAuth/MFA flow itself.
- No full code review: SAST is pattern-based, about 35 rules, JS/TS, Python, PHP.
- No cloud account-level IAM auditing (ScoutSuite/Prowler style).

Code-level safety rules that are consistent across modules: GET-only crawling, forms never submitted, logout/delete/cart links never followed, subdomain tooling passive only, buckets tested only if referenced by the target's own page, Supabase tables read as counts only, storage and Firebase stores read as one name at most (never a value or file), secrets redacted and never stored.
